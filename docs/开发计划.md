# 本地音乐标签库 + 和声分析工作台 · 开发计划 v3

> 依据：`神鹿谣分析.json`（真实样本）+ `instrument.xlsx`（43 项乐器）+ Elite Music Manager 截图（界面参考）  
> 技术栈：Electron + Vue3 + Vite + SQLite(better-sqlite3) + 手写 CSS  
> 本文是规格书：建表语句、换算公式、JSON 治理规则、验收断言都可直接用于实现。

## 0. 一页结论

| 判断                | 结论                                                |
| ----------------- | ------------------------------------------------- |
| 最大风险              | 不是技术，是**给"音乐描述"设计完备格式**——这条路你自己已经走到迷路了            |
| 破法                | 标准只承诺"结构怎么变都不炸"，不承诺"语义完备"。核心键砍到 6 个               |
| JSON 与 SQLite 的关系 | JSON 是**源**（可手改、可 diff、可版本控制），SQLite 是**索引**（可重建） |
| 词表放哪              | 放 JSON（你的直觉对），SQLite 里只是它的缓存                      |
| 网格关键              | tick + 统一时间轴标记 + 稀疏事件；调性与段落都属于时间轴                 |
| 泳道                | 配置驱动，不是写死 4 条。数据层已经支持，只需渲染层跟上                     |
| 上次失败原因            | 不是模型能力，是**没有验收标准**                                |

### v2 → v3 的三处修正

1. **新增整套 JSON 治理规则**（§1）：版本号、只增不删、迁移链、fixture 回归、字段日志。这是解决"越写越迷失"的正解。
2. **词表从 SQLite 改为 JSON 源 + SQLite 缓存**（§3）：你提出用 JSON 维护词表，比 SQLite 更合适——但必须解决"手改后库里引用悬空"的问题。
3. **新增 `audio_offset_ms`**（§5.2）：导出音频前后有留白，网格原点不等于音频 0 点，不建模就永远对不齐。

## 1. JSON 格式怎么维护（大公司真正在做的）

### 1.1 先纠正一个认知

你以为大公司有一个"完备的格式设计"，然后严格维护它。**不是。** Protobuf 从 2008 年到现在，核心设计目标只有一条：*让结构演化不破坏旧读取器*。它压根不试图描述"音乐是什么"。

你现在做的事，相当于一个人从零写 protobuf——而且还要同时定义"音乐本体论"。迷失是必然的。

### 1.2 八条可执行规则

**① 版本号写在数据里，不写在代码里**

```json
{ "schemaVersion": 3, ... }
```

每次读文件先读这个数字。**没有版本号的文件，一年后你自己都不知道该怎么读。**

**② 只增不删，名字永不复用**

- 字段要废弃 → 标记 `"_deprecated": "改用 key_name"`，读取逻辑保留两个版本
- 永远不要把 `tempo` 这个词改去表示别的东西（旧文件会静默解读错）
- 必须删时，写进 `reserved` 列表，记下"这个键以后不许再用"

**③ 新字段必须可选，缺省语义明确**

缺省 = `null`（表示"没记录"），不是 `""`（表示"记录了一个空值"）。你的 JSON 里 `instruments_used: ["", ...]` 就是这两者混淆的产物。

**④ 迁移是纯函数链，每步只做一件事**

```ts
type Migration = (doc: any) => any;

const chain: Record<number, Migration> = {
  1: v1_to_v2,   // 把 "period:" 改名为 period
  2: v3_to_v4,   // 把 instruments 从字符串数组改成 {name, family}
};

function migrate(doc: any): any {
  let v = doc.schemaVersion ?? 1;
  while (chain[v]) { doc = chain[v](doc); v++; doc.schemaVersion = v; }
  return doc;
}
```

每个迁移函数都能单独写测试：喂一个旧样本，断言输出。**这是唯一能让"以后还要变"不变成灾难的机制。**

**⑤ 每个历史版本留一个 fixture，CI 断言全都还能读**

```
fixtures/
  shenlu.v1.json    ← 你现在这份
  shenlu.v2.json
  samples/minimal.json
```

测试写一句：`for each fixture → migrate(doc) → 断言核心字段存在`。三年后你改格式，这个测试会告诉你有没有把老文件读坏。

**⑥ 线格式 ≠ 内存模型**

读进来立刻转成内部类型（`Track`、`AnalysisDoc`），之后所有业务代码只认内部类型。**JSON 里叫什么、内部叫什么，允许不一样。** 这样外部格式怎么变，影响范围都被压缩在一个 `importer.ts` 里。

**⑦ 未定型的东西先放 `extra`，用够三次再提升**

不要为了一个一次性的想法改 schema。先在 `extra` 里塞，等你第三次需要它、并且发现每次都在重复同样的处理时，才提升为正式字段。**这条规则能挡掉 80% 的格式膨胀。**

**⑧ 每次变更留一行"为什么"**

`docs/schema-log.md`：

```
v2 2026-10-18  section 与 tonality 合并进 timeline：因为它们总在同一小节出现，拆开要靠小节号猜关联
v3 2026-10-20  instruments 改为对象：需要记录声部（Violins 1/2）
```

三个月后你就靠这张表回忆"当初为什么"。这是你这次最需要的补丁。

### 1.3 关于"为了白嫖云服务改格式"这件事

这是最容易把数据资产抵押出去的操作。规则：

> **你的 JSON 是资产，云服务是可替换的管道。任何外部字段名都不许直接出现在核心 JSON 里。**

判断标准一句话：**把那个服务换掉，你的文件还能不能读？** 不能，就是耦合了。  
需要对接时写一个 adapter（`adapters/google-sheets.ts`），把外部结构翻译成你的内部模型。adapter 可以随时删，核心格式不动。

### 1.4 最小核心集（给你一个"不许再加"的锚）

一份曲目分析的 JSON，核心只留 6 个键：

```json
{
  "schemaVersion": 3,
  "title":   { "original": "神鹿谣", "lang": "Chinese" },
  "basic":   { "meter": "3/4", "bpm": 107, "description": "..." },
  "tags":    { "instrument": [...], "technique": [...] },
  "timeline":[...],
  "events":  [...],
  "extra":   { }
}
```

**凡是这 6 个装不下的，先进 `extra`。** 这句话是防止你再次迷路的绳子。

## 2. 数据模型（schema v1）

### 2.1 曲目

```sql
CREATE TABLE track (
  seq        INTEGER PRIMARY KEY AUTOINCREMENT,  -- 内部：关联、分页、FTS rowid
  id         TEXT NOT NULL UNIQUE,               -- 对外 UUID
  title      TEXT NOT NULL,
  title_lang TEXT,
  title_sort TEXT,
  composer   TEXT,
  performer  TEXT,
  album      TEXT,
  genre      TEXT,
  period     TEXT,
  duration_ms INTEGER,
  file_path  TEXT,                               -- 可空：先建档后找文件
  file_hash  TEXT,
  notes      TEXT,
  extra      TEXT,                               -- JSON：未定型字段
  added_at   INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  deleted_at INTEGER
);
CREATE INDEX ix_track_sort ON track(title_sort);
```

### 2.2 标签（缓存表，源在 JSON）

```sql
CREATE TABLE tag (
  id          TEXT PRIMARY KEY,      -- 来自 vocab JSON，永不变
  dim         TEXT NOT NULL,
  name        TEXT NOT NULL,
  display     TEXT,
  merged_into TEXT REFERENCES tag(id),
  created_at  INTEGER
);

CREATE TABLE tag_edge (              -- 多父（DAG）
  child_id  TEXT NOT NULL,
  parent_id TEXT NOT NULL,
  PRIMARY KEY (child_id, parent_id)
);

CREATE TABLE tag_alias (
  alias  TEXT NOT NULL,
  dim    TEXT NOT NULL,
  tag_id TEXT NOT NULL,
  PRIMARY KEY (alias, dim)
);

CREATE TABLE track_tag (
  track_id TEXT NOT NULL,
  tag_id   TEXT NOT NULL,
  weight   REAL DEFAULT 1,
  PRIMARY KEY (track_id, tag_id)
);
CREATE INDEX ix_tt_tag ON track_tag(tag_id);
```

**验收标准（很重要）**：`DELETE FROM tag; DELETE FROM tag_edge;` 后重启应用，能由 `vocab/*.json` 完整重建。做不到，就说明"缓存"这个定位是假的。

### 2.3 分析与时间轴

```sql
CREATE TABLE analysis (
  id              TEXT PRIMARY KEY,
  track_id        TEXT NOT NULL,
  title           TEXT,
  ppq             INTEGER NOT NULL DEFAULT 480,
  tempo_value     REAL,
  tempo_unit      TEXT,
  meter_num       INTEGER,
  meter_den       INTEGER,
  meter_type      TEXT,
  meter_note      TEXT,
  audio_offset_ms INTEGER NOT NULL DEFAULT 0,  -- tick 0 对应的音频毫秒
  view_id         TEXT,                        -- 当前使用的泳道方案
  author          TEXT,
  created_at      INTEGER,
  updated_at      INTEGER,
  deleted_at      INTEGER
);

CREATE TABLE analysis_marker (
  id          TEXT PRIMARY KEY,
  analysis_id TEXT NOT NULL,
  tick        INTEGER NOT NULL,
  kind        TEXT NOT NULL,      -- meter | tempo | section | key | rehearsal
  label       TEXT,
  num         INTEGER,
  den         INTEGER,
  bpm         REAL,
  key_name    TEXT,
  confidence  TEXT DEFAULT 'confirmed',  -- confirmed | uncertain | guess
  note        TEXT,
  sort_order  INTEGER DEFAULT 0,
  UNIQUE(analysis_id, kind, tick)
);
CREATE INDEX ix_marker ON analysis_marker(analysis_id, kind, tick);

CREATE TABLE analysis_event (
  id          TEXT PRIMARY KEY,
  analysis_id TEXT NOT NULL,
  lane        TEXT NOT NULL,      -- 任意字符串，由 view 定义
  tick        INTEGER NOT NULL,
  dur_ticks   INTEGER NOT NULL DEFAULT 480,
  text        TEXT NOT NULL,
  confidence  TEXT DEFAULT 'confirmed',
  updated_at  INTEGER
);
CREATE INDEX ix_event ON analysis_event(analysis_id, tick);
```

**为什么段落、调性、拍号、速度共用一张表**：它们唯一的共同点是"从某个 tick 起生效"，而这正是渲染需要的全部信息。`WHERE kind = ?` 隔离，互不污染。

### 2.4 全文索引

```sql
CREATE VIRTUAL TABLE track_fts USING fts5(
  title, composer, performer, album, notes,
  content='', tokenize='unicode61 remove_diacritics 2'
);
```

- rowid = `track.seq`，与曲目写入同一 transaction 双写
- **不用 trigram**：它要求查询串 ≥3 字符，「钢琴」两字直接返回空。西文标题用 `unicode61`，中文短词用 `LIKE` 兜底
- 标签不进 FTS

### 3.2 instrument.json 结构（嵌套树，便于手写）

```json
{
  "schemaVersion": 1,
  "dim": "instrument",
  "roots": [
    {
      "id": "woodwind", "name": "木管",
      "children": [
        { "id": "flute", "name": "Flute", "aliases": ["长笛", "flute"] },
        { "id": "oboe",  "name": "Oboe",  "aliases": ["双簧管"] }
      ]
    },
    {
      "id": "chinese", "name": "民族乐器",
      "children": [
        { "id": "pipa",    "name": "Pipa (5-Strings)", "aliases": ["琵琶", "Pipa"] },
        { "id": "konghou", "name": "Konghou", "aliases": ["箜篌"] },
        { "id": "erhu",    "name": "Erhu",    "aliases": ["二胡"] },
        { "id": "yangqin", "name": "Yangqin", "aliases": ["扬琴"] },
        { "id": "dizi",    "name": "Dizi",    "aliases": ["笛子", "竹笛"] }
      ]

```

嵌套树比"平铺 + 边列表"好手写；启动时展平成 `tag` + `tag_edge`（父 = 所在层的根或节点）。

### 3.3 手改之后怎么不崩

这是 JSON 词表方案唯一的真风险：你在编辑器里删了一个标签，库里还有曲子引用它。

**处理规则（不要自动清理）**：

1. 启动时同步：JSON 有、库没有 → 插入；JSON 有、库也有 → 更新 name/alias
2. 库里有引用、但 JSON 里没有 → **不删**，写进「孤儿报告」页
3. 孤儿报告每项给两个按钮：`重新加回词表` / `清除引用（曲目会失去这个标签）`

**绝不静默删除**——手滑一次就丢一批标注，这是不可接受的。

### 3.4 写入格式化（让 diff 好看）

UI 新建标签时写回 JSON，必须保持：固定 key 顺序（`id, name, aliases, children`）、2 空格缩进、UTF-8 无 BOM、每项一行（短对象不换行）。这样 `git diff` 每次只显示一行变化，而不是整文件重排。

### 3.5 输入补全的匹配顺序

1. 别名精确命中（`pianoforte` → piano）
2. 同维度前缀/子串（`pia` → piano）
3. 编辑距离 ≤2（`pniano` → piano）
4. 都没命中 → 允许新建，弹「新建 instrument:pniano？」

第 4 步的确认框是**唯一真正防脏的地方**：只在你真要犯错时出现。

## 4. 检索

### 4.1 三路合并

```
输入 → 解析
  ├─ 「dim:value」   → 标签过滤（关系表）
  ├─ 普通词 ≥3 字符   → FTS5
  ├─ 普通词 <3 字符   → LIKE
  └─ 混合            → 交集
```

多标签 AND：

```sql
SELECT t.* FROM track t
JOIN track_tag tt ON tt.track_id = t.id
JOIN tag g ON g.id = tt.tag_id
WHERE g.name IN ('piano','melancholy') AND t.deleted_at IS NULL
GROUP BY t.id
HAVING COUNT(DISTINCT g.name) = 2;
```

比截图里「两个空格分隔当 AND」靠谱，且支持否定 `-instrument:piano`。

### 4.2 性能分阶段

- **第一阶段**：主表直查 + `LIMIT 200` + 前端虚拟滚动。5000 条内 <50ms，**不需要投影表**
- **第二阶段**（>2 万条）：加物化投影表，启动读首屏，异步补详情

## 5. 网格

### 5.1 换算公式

```ts
// tick → 第几小节第几拍
function tickToBarBeat(ms: Marker[], tick: number, ppq: number) {
  const m = markerAt(ms, 'meter', tick)!;
  const barLen = ppq * m.num! * 4 / m.den!;
  const rel = tick - m.tick;
  return {
    bar:  m.startBar! + Math.floor(rel / barLen),
    beat: Math.floor((rel % barLen) / ppq) + 1,
    off:  (rel % barLen) % ppq,
  };
}
// tick → 秒：按 tempo 分段积分；tick → 音频毫秒：+ audio_offset_ms
```

`startBar` 在保存 marker 时算好存进去，否则每次换算都要从头累加，慢且容易差一。

### 5.2 用你的数据验算（**我上次算错了，这里更正**）

3/4、107 BPM、ppq=480 → 每小节 = 3×480 = 1440 tick，1.6822 秒。

| 位置               | tick   | 时间      |
| ---------------- | ------ | ------- |
| intro（第 2 小节）    | 1440   | 1.68s   |
| A1（第 12 小节）      | 15840  | 18.50s  |
| Transition 1（26） | 36000  | 42.06s  |
| A2（56）           | 79200  | 92.52s  |
| coda（106）        | 151200 | 176.61s |

我上次说「全曲 178 秒」是错的——**178 秒是 coda 的起点，不是结尾**。  
实际 3:06 = 186 秒 → 186s ÷ 1.6822 = **110.6 小节**。coda 从 106 开始，到 110 结束，4.5 小节，完全自洽。

**结论：你的 3/4 和 107 BPM 是对的，数据没问题。是我表述误导了。**

### 5.3 音频偏移（新增，必须建模）

导出时前后留了余量，所以：`网格第 1 小节 ≠ 音频 0 秒`。

```
音频位置(ms) = audio_offset_ms + tickToMs(tick)
```

`audio_offset_ms` 默认 0，界面上给一个数字输入框 + 「用当前播放位置设为原点」按钮。没有这个字段，播放头永远差一两秒，越到后面越明显。

**验收**：设 offset = 1500ms，第 1 小节第 1 拍应落在音频 1.5s；重开应用后位置不变。

### 5.4 渲染

- **canvas**，不用 DOM 表格（细分到十六分音符时 DOM 会爆）
- 三层：网格线 → 事件文本 → 覆盖层（播放头/选区）
- 只画视口内小节；垂直方向按泳道高度累加
- 高 DPI：`canvas.width = cssW * dpr`、`ctx.scale(dpr,dpr)`、1px 线 0.5 偏移
- 顶部两条带：段落条（section）、调性条（key）

## 6. 动态泳道（回答"能不能加一行"）


### 6.1 现状：数据层已经是动态的

`analysis_event.lane` 就是普通字符串，没有任何 CHECK 约束。**加泳道不需要改表结构。** 需要动态化的只有渲染层。

### 6.2 泳道方案放 JSON，可切换

`data/views/roman.json`：

```json
{
  "schemaVersion": 1,
  "id": "roman",
  "name": "罗马数字（古典）",
  "group": "harmony",
  "lanes": [
    { "id": "chord",     "label": "和弦", "kind": "text", "height": 30, "align": "left" },
    { "id": "inversion", "label": "转位", "kind": "text", "height": 22, "align": "center" },
    { "id": "function",  "label": "功能", "kind": "text", "height": 22, "align": "center" },
    { "id": "bass",      "label": "低音", "kind": "note", "height": 22 }
  ]
}
```

`data/views/pop.json`：`chord`（G7）/ `bass` / `note`——同一批事件，换一套泳道就是另一套分析视角。

**关键**：一个曲目可以有多套 view，切换显示。事件本身不绑定 view，`lane` 只是字符串，所以两套 view 可以共享同名泳道（`chord`）的内容。

### 6.3 "加一行"的实现路径

| 需求 | 做什么 | 要改代码吗 |
|---|---|---|
| 加一条文本泳道（如「织体」）| JSON 里加一条 lane | 不用 |
| 改泳道高度/顺序 | 改 JSON | 不用 |
| 加一条音符型泳道（如「低音线」）| 用 `kind: "note"` | 不用 |
| 加一种全新渲染（如钢琴卷帘、力度曲线）| 新写一个 renderer 注册进 `kind` | 要，但只新增文件 |

这就是他要的"动态灵活"：**90% 的调整是改 JSON，10% 是加插件**。

### 6.4 泳道的三个分组（v1 够用）

```
和声：chord / inversion / function / bass
结构：section（以 marker 形式画成顶部条，不是泳道）
备注：note（自由文本，可跨多拍）
```

配器那组（orchestration / texture）先不做，但 `views/*.json` 的机制已经能装下——以后加一个 `orchestration.json` 即可。

## 9. 导入器（JSON → 数据）

### 9.1 流程

```
读文件 → 取 schemaVersion → 跑迁移链 → 校验（JSON Schema）
      → 展平标签（词表匹配 + 未命中标记）
      → 生成清洗报告（不静默改，逐条列给你看）
      → 你确认 → 写库 → 原文件备份为 .bak
```

### 9.2 针对你这份样本的清洗规则

| # | 现象 | 处理 | 是否需你确认 |
|---|---|---|---|
| 1 | `"period:"` 带冒号 | 归一为 `period` | 是（记日志） |
| 2 | `instruments_used` 含 `""` | 丢弃空串 | 否 |
| 3 | 两个 `"section 8"` | 段落用 id 区分，label 保留原样 | 是（提示编号重复）|
| 4 | `"not sure, is f natural minor?"` | `key_name="f natural minor"`, `confidence="uncertain"`, `note` 存原文 | 是 |
| 5 | `{"parent": ["imitation","canon"]}` | 生成两条 `tag_edge` | 是（确认父类语义）|
| 6 | `Pipa (5-Strings)` | `display` 保留原串，别名补 `Pipa` | 否 |
| 7 | 时间签名 `description` 是模糊表述 | 存 `meter_note`，不参与计算 | 否 |
| 8 | `start_position_musical` | `(bar-1) × barLen` 转 tick | 否 |

**清洗报告是产品的一部分**：每一处修正都列出来让你点确认。这才是"容忍脏数据"——不是放任，是让脏变可见、可变、可回溯。
